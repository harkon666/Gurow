## Problem Statement

Gurow's current editor exposes persistent left and right sidebars, technical Skill identifiers, save revision numbers, implementation labels, and a GPU-failure simulation control. These distract from learning and reduce the space available for the Canvas Document. Authors cannot currently create Prerequisites by dragging directly between Skill cards, and Tasks appear as lists rather than an adaptable work board.

Personal learners, Coaches preparing learning content, and enrolled Learners need a clearer interface without losing existing learning, editing, recovery, accessibility, and review capabilities. A single generic “Done” state would be misleading: personal Task completion, Coach material readiness, Learner working progress, Approval, XP, and Mastery are different concepts.

## Solution

Make the canvas the primary Skill navigation surface, replace permanent sidebars with a compact labeled toolbar and on-demand panels, and provide direct pointer-based Prerequisite creation. Selecting a Skill opens a temporary summary; “Open board” opens that Skill's spacious Task Board. Returning restores the canvas position and zoom.

Provide customizable Task Boards in all three contexts in this release, not personal mode only. Personal boards connect a designated Completion Column to personal Task completion. Coach Draft boards organize material preparation. Learner boards organize personal work within one Enrollment, separately from Submissions and Reviews. Preserve all existing ownership, learning, retention, Version, and recovery rules.

Remove implementation-oriented UI while retaining honest saving/error/conflict feedback and meaningful learning history. Support narrow-screen layouts and keyboard/non-drag operation, including when WebGPU is unavailable.

## User Stories

1. As a canvas user, I want no permanently open sidebars, so that the Canvas Document has more usable space.
2. As an author, I want a labeled “Add Skill” toolbar action, so that creating a Skill remains discoverable.
3. As a user, I want a labeled “Skill list” action with search and keyboard navigation, so that I can locate Skills without scanning the canvas.
4. As an author, I want secondary actions such as copying from a Learning Path in a “More” menu, so that reduced chrome does not remove functionality.
5. As a user, I want to select a Skill and open a dismissible summary, so that I can inspect its learning outcome and requirements without permanently losing canvas space.
6. As a user, I want an explicit “Open board” action from that summary, so that a normal selection does not unexpectedly navigate away.
7. As a user, I want to return from a Task Board to my prior canvas position and zoom, so that I retain my place.
8. As an authorized author, I want dragging a Skill card body to move it and dragging its edge connection point to connect it, so that the gestures are distinct.
9. As an author, I want connection points visible on hover or selection, so that I can discover connections without constant visual clutter.
10. As an author, I want to create A → C and then B → C, so that I can express that both Skills are Prerequisites of C.
11. As an author, I want valid destinations highlighted and invalid connections explained, so that I understand why a connection is rejected.
12. As an author, I want to select and delete a connection and undo that deletion, so that graph editing is recoverable.
13. As a keyboard user, I want a non-drag connection action from Skill details, so that creating and removing Prerequisites does not require a mouse gesture.
14. As a learner, I want the current Access and Mastery rules retained, so that a UI redesign does not silently alter my learning requirements.
15. As a user, I want each Skill to have its own Task Board, so that its work remains attached to the correct learning outcome.
16. As a board owner, I want to add, rename, reorder, and remove columns, so that I can organize my work in my own terms.
17. As a board owner, I want to choose a destination for Tasks before removing their column, so that column deletion never deletes Tasks.
18. As a personal learner, I want Backlog, To Do, In Progress, and Done as initial columns, so that the board is useful immediately.
19. As a personal learner, I want one designated Completion Column whose label can change, so that completion does not depend on spelling a column “Done.”
20. As a personal learner, I want entering or leaving that column to complete or uncomplete the Task under existing XP rules, so that my board and learning progress agree.
21. As a personal learner, I want a replacement Completion Column required before deleting it, so that the board retains an unambiguous completion destination.
22. As a personal learner, I want Mastery to remain an explicit separate action, so that finishing Tasks does not claim that I have mastered the Skill.
23. As an authorized Task author, I want a required title and optional description with add/edit/reorder/move operations, so that the initial board remains lightweight.
24. As an authorized Task author, I want safe deletion with an undo opportunity for eligible Tasks, so that an accidental deletion can be corrected without bypassing retention rules.
25. As a user, I want archived Tasks and learning history to remain accessible separately from active cards, so that tidying the board does not erase evidence or rewards.
26. As a Coach, I want Draft columns initially named Ideas, In preparation, and Ready, so that I can organize material readiness rather than Learner progress.
27. As a Coach, I want Draft column placement independent of publication eligibility, so that “Ready” is not a hidden publishing rule.
28. As a Coach, I want a separate “Review” entry point, so that assessing learner work is not confused with preparing Tasks.
29. As a Learner, I want my own board columns and card positions per Skill and Enrollment, so that my organization does not change someone else's board.
30. As a Learner, I want Done to mean I have finished working, so that I can track my own activity without impersonating the Coach's Approval.
31. As a Learner, I want an explicit “Submit for review” action, so that moving a card never silently submits my work.
32. As a Learner, I want review status visible on cards and in the Skill summary, so that unsent, pending, changes-requested, and approved evidence are understandable independently of my columns.
33. As a Learner, I want review outcomes not to move my cards automatically, so that my personal organization remains under my control.
34. As a Coach and Learner, I want valid earlier Approval and the newest Submission Revision's status represented accurately, so that a newer pending revision does not falsely erase existing evidence.
35. As a Coach, I want official Task definitions editable only through authorized Draft authoring, so that learner board customization cannot mutate a published Version.
36. As an existing user, I want completed personal Tasks and approved learner Tasks initially placed in Done, so that introducing boards respects existing progress.
37. As an existing user, I want other active personal/learner Tasks initially placed in Backlog and Draft Tasks in their first column, so that migration is predictable.
38. As a user, I want board changes to survive reopening and reload without leaking across Accounts, Skills, or Enrollments, so that my organization is durable and correctly scoped.
39. As a user, I want readable save status without technical revision numbers, so that I know whether my work is safe without implementation noise.
40. As a user, I want failures and stale-save conflicts surfaced with retained local work, so that simplified chrome never disguises data loss.
41. As a user, I want technical Skill IDs, implementation labels, and the GPU-failure simulation button removed from user-facing UI, so that the interface uses learning vocabulary.
42. As a learner, I want meaningful Learning Path Versions and Submission history still accessible, so that hiding save counters does not hide my learning contract.
43. As a narrow-screen user, I want full-screen Skill details and a horizontally navigable board with a column selector, so that learning workflows remain usable.
44. As a keyboard or non-drag user, I want menu/selection alternatives to connection and Task movement gestures, so that the primary workflows are not mouse-only.
45. As a user without a working GPU canvas, I want the Skill list, Tasks, Submissions, Reviews, and recovery actions still accessible, so that renderer failure does not block learning or discard my document.

## Implementation Decisions

1. **Scope and relationship to the existing product.** This is a new cross-cutting UX specification for personal use, Coach authoring, and Learner participation together. It supersedes the permanent-sidebar presentation described in the original MVP spec, not its learning contract, architectural ownership, delivery gates, or data-retention rules. Existing functionality must be relocated rather than silently removed. Implementation tickets will be sliced separately.

2. **Navigation shell.** Use labeled primary toolbar actions “Tambah skill” / Add Skill and “Daftar skill” / Skill list, plus “Lainnya” / More for secondary actions. Labels are functional examples, not a requirement to introduce a new localization system. The Skill list provides search and keyboard selection. A Skill selection opens a dismissible summary with outcome, incoming/outgoing relationships, learning state, and applicable actions. “Buka board” / Open board opens a spacious board, with return navigation preserving the camera. Keep copy/reuse, Skill deletion where permitted, Required/Enrichment settings, Access/Mastery/XP controls, archival history, Submissions, Reviews, and recovery reachable in the appropriate context. Coach review has an explicit separate Review entry point.

3. **Direct connections.** Card-body dragging retains position-editing behavior where authorized; dragging a connection point creates an edge. Points appear on hover or selection, valid targets are highlighted, and an edge is committed only after a valid drop. Cancelled or rejected gestures leave the graph unchanged. Create A → C and B → C separately; bulk connection creation is not included. Reject self-connections, duplicates, missing or cross-context endpoints, cycles, and applicable Coach content-rule violations with concise feedback. Selecting an edge supports deletion and undo. The existing non-drag detail action remains a first-class alternative. Both paths use the same authoritative graph and validations.

4. **Editor ownership and learning permissions.** Extend the existing editor interaction/command boundary rather than introducing a second authoritative React canvas graph or replacing the Rust/WebGPU editor. One completed editing gesture is one undo step; editor history does not rewind learning history. Prerequisites retain ALL semantics: both A and B must have Mastery for C's prerequisite condition. XP Thresholds and Access Overrides remain independent existing checks. Learners do not gain permission to reposition shared Canvas Layout cards or edit a published Prerequisite Graph. Authorized Coach layout edits remain separate from immutable published content. Controls reflect permissions and the backend enforces them.

5. **Task Board model.** A board organizes active Tasks of exactly one Skill using ordered, identifiable columns and ordered card membership. The card refers to the existing Task rather than copying its learning records. Persist board organization through the existing application/backend boundary, separately from engine geometry, Submissions, Reviews, and published learning definitions. Scope personal boards to their owning Account and personal Skill, Coach preparation boards to the authorized Draft and Skill, and learner boards to the Enrollment and versioned Skill. Learner column/card changes do not affect any other Enrollment or the Coach's preparation board. Internal IDs remain necessary but are not user-facing identifiers. Exact table names, endpoint paths, and request shapes remain implementation choices; the contracts below are mandatory.

6. **Column operations.** Support add, rename, reorder, and remove per board. Removing a populated column requires a surviving destination and preserves all its Tasks. Do not silently drop cards or learning records. Retain a usable board rather than allowing deletion of its last remaining column. Distinguish column identity/role from display name. Column edits persist across reopening and must not reset another board or a previously customized board.

7. **Personal completion coupling.** Initial columns are Backlog, To Do, In Progress, Done, with exactly one designated Completion Column initially named Done. Entering it completes the Task; leaving it undoes completion under existing permissions, XP Award/Correction rules, and backend confirmation. Repeated moves/retries cannot multiply XP, and neither direction automatically changes personal Mastery. Renaming the column does not change its role. Removing it requires a replacement and an explicit Task destination before applying the change. Treat any personal card placement across the completion boundary, including column-removal relocation, consistently with completion; never leave persisted membership and completion contradicting each other. A column-role replacement must reconcile the affected Tasks as one coherent validated change, with its consequences visible before confirmation. Any retained alternate completion action must keep the board consistent rather than create a second independent completion truth.

8. **Coach preparation.** Initial Draft columns are Ideas, In preparation, Ready (Ide, Sedang disusun, Siap). They represent material preparation only, may be customized, and do not grant XP, set Approval, or gate publication by their labels or placement. Coach Draft card positions are not copied as learner progress. Required/Enrichment designation, rewards, and publication validation remain available and unchanged; lightweight title/description authoring does not remove existing domain fields.

9. **Learner organization and evidence.** Initial learner columns are Backlog, To Do, In Progress, Done. Column placement is a learner-controlled working state, not an Approval/Submission state machine. Moving to Done records finished working only; leaving it does not revoke evidence, XP, or Mastery. Sending requires an explicit Submit for review action, and approval/revocation remains an authorized Coach action. No Review outcome, including Changes Requested, moves the learner card automatically. Display clear review status on the card and Skill summary, including Changes Requested while a card remains Done. Represent newest-revision status and an earlier still-valid Approval without falsely collapsing them into one exclusive board status. Existing Access, inactive Enrollment, Submission Draft privacy, and review-eligibility rules remain enforced; board customization grants no new authority to work or submit.

10. **Task authoring and removal.** New Task authoring requires a title and offers an optional description. Authorized personal owners and Draft authors can add, edit, order, and move Tasks; learners cannot edit official Task definitions or add private Tasks to an Enrollment in this release. Column movement never changes Task ownership to another Skill. Provide deletion undo for Tasks that are eligible for deletion, validating the restored edit through the normal save path. Tasks with history follow existing Archival instead of destructive deletion. Archival is an explicit revision-checked action, remains separate from document saving, and is not reversible through this board's undo. Archived Tasks remain in retained history, not active columns. Do not promise restoration that conflicts with the accepted archival contract.

11. **Durability and conflict handling.** Successful board operations must survive reload and remain isolated to their authorized context. Validate membership and column targets on the server. Completion-coupled moves must not partially persist a new column while failing the corresponding completion/XP update. Competing or stale edits must not silently overwrite newer organization, bypass ownership checks, or lose Task records. Surface errors/conflicts in user language and retain recoverable local intent; do not claim backend success before confirmation. Existing save-revision protection remains even though its numeric value is hidden.

12. **Initial placement of existing Tasks.** Initialize boards from existing records once, without replaying completion or Approval actions: completed active personal Tasks → Done; active learner Tasks with at least one valid Approval → Done; other active personal/learner Tasks → Backlog; existing Draft Tasks → the initial preparation column. Preserve review/submission status on cards, including newer pending revisions alongside valid earlier Approval. Preserve relative existing Task order within each initial column where available. Archived Tasks remain excluded from active boards and accessible as history. Initialization must not award/revoke XP, change Mastery, rewrite a published Version, or rerun later in a way that resets customization. Concurrent/repeated initialization must produce one coherent board, not duplicate columns/cards.

13. **Technical chrome.** Remove the user-facing Simulate GPU Failure control, technical Skill ID presentation, save-revision counters, and implementation labels such as Rust Owned and React Domain Payload. Keep meaningful saving/saved/error/conflict states, recovery/retry actions, Learning Path Version information, and Submission Revision history accessible. Hiding technical values is a presentation decision, not deletion of IDs, revisions, diagnostics, or concurrency validation. Fault injection remains available to the test harness rather than ordinary product chrome.

14. **Responsive and accessible presentation.** Narrow screens use full-screen Skill details/dialogs and a horizontally navigable Kanban with a column selector. Provide keyboard-operable menu/selection alternatives for moving Tasks and creating/removing connections, visible focus, sensible focus restoration after dismissing panels, and readable validation feedback. Temporary navigation remains available without WebGPU. This extends the application's responsive learning UI; it does not introduce a WebGL renderer or a touch-gesture rewrite of the GPU canvas. Preserve the existing renderer-recovery contract and CPU-side document.

15. **Domain documentation.** Record Task Board, Task Board Column, and Completion Column vocabulary and the separation of board organization from assessment. Preserve the existing ADR decisions on immutable Versions, evidence-based coach Mastery, authoritative Rust editor state, revision-checked saving, list fallback, and archival. Narrow-screen application access does not supersede the deferred mobile canvas gesture scope.

## Testing Decisions

The user approved these boundaries: browser/application behavior as the primary proof, backend API requests against real PostgreSQL for durable domain and authorization behavior, and public Rust editor commands/outputs as focused supplementary proof. Do not add a new internal test seam merely to expose implementation details.

1. **Good tests.** Assert user-visible outcomes, accepted/rejected requests, actual restored state, permissions, and retained history. Avoid coupling acceptance to component internals, CSS class names, private Rust state, SQL statement order, or mocked XP calculations. Exercise real pointer/keyboard workflows; a direct engine command cannot prove that a drag handle works. After saving, reload and inspect the newly loaded application, not just unchanged storage bytes.

2. **Existing prior art.** Reuse the existing Puppeteer/Chromium functional browser checks: T06 covers creation, connections, rejection, undo/reload, recovery, and list fallback; T17 covers authenticated personal tracking, XP correction, failed/retried writes, keyboard access, and reload; T18/T19 cover Coach Draft authoring and publication. Existing backend personal-tracking, coach-authoring, enrolled-version, submission, review, archival, and deletion suites use public application requests and real database fixtures. Public engine-core tests cover editor commands, geometry, and graph invariants. These are patterns to extend, not evidence that new acceptance is already covered.

3. **AC-01 — Navigation preservation.** In the applicable personal, Draft, and enrolled contexts, no permanent sidebars remain. Add Skill, searchable Skill list, More, authorized secondary actions, Skill summary, board navigation, and separate Coach Review remain reachable. Selecting two different Skills opens the correct Tasks. Returning from a board preserves the camera. Assert meaningful existing actions remain available rather than testing only that sidebars disappeared.

4. **AC-02 — Pointer and graph behavior.** Create fresh A/B/C Skills through the UI, move a card by its body, then drag two separate prerequisite edges into C. Check destination feedback, direction, persisted reload, delete/undo/redo, and graph unchanged after cancelled drag, self-edge, duplicate, missing/invalid target, cycle, or unauthorized edits. Cover camera zoom/pan so handle hit testing is not valid only at the initial viewport. Confirm the non-drag path produces the same graph results and keeps ALL/Access rules unchanged.

5. **AC-03 — Board operations.** Create/edit Tasks with title and optional description, reorder cards within a column, move between columns by drag and non-drag controls, and customize columns. Delete an occupied column only after selecting its destination; all Tasks survive and the board remains usable. Reload to prove order, labels, membership, and Skill association persist. Exercise empty-board/empty-column states, failed saves, and invalid column/Task references.

6. **AC-04 — Personal completion.** Move into/out of a renamed Completion Column and assert actual completion, correct XP adjustment, and unchanged Mastery. Repeat/retry operations without duplicate rewards. Exercise completion-column removal/replacement and moving Tasks through column deletion so membership and completion remain coherent. Reject failures atomically; do not show durable success for a rejected learning action. Check permissions/Access through the same existing domain boundary.

7. **AC-05 — Coach preparation.** Confirm initial preparation columns and customization. Move a Task to Ready and prove no learner progress or Approval changed and no new column-based publishing gate appeared. Keep official Task editing in the Draft, preserve published Version immutability and Required/Enrichment/reward settings, and reach the existing review workflow from its separate entry point.

8. **AC-06 — Learner and review independence.** With two Learners/Enrollments, customize one board and prove the other board and Coach Draft remain unchanged. Move a card to Done without creating a Submission, Approval, XP, or Mastery. Explicitly submit, request changes, approve, submit a newer revision, and revoke approval through authorized actions; board placement remains learner-controlled, while card and summary review status remains correct. Verify a valid earlier Approval can coexist with a newest pending revision. Unauthorized definition edits and access to another learner's board are rejected; private Submission Draft contents remain private.

9. **AC-07 — Initialization and retention.** Seed old personal completed/incomplete Tasks, learner approved/unapproved Tasks including a newer pending revision, Draft Tasks, and archived history. Check their defined initial placement and ordering, unchanged XP/Mastery/Approvals/Versions, absence of archived active cards, repeat/concurrent initialization safety, and preservation of subsequent customization. Test eligible Task deletion and undo separately from archival; undo cannot resurrect archived content.

10. **AC-08 — Persistence and isolation.** Exercise reopen, reload, competing tabs, stale or rejected writes, wrong Account/Path/Skill/Enrollment, and operation retries through the API/database seam and representative browser journeys. Assert no lost Tasks, cross-context memberships, partial completion moves, duplicated XP, or hidden overwrites. Preserve rejected local work under the proper identity boundary.

11. **AC-09 — Clean chrome and meaningful history.** Confirm user-facing views do not show technical Skill IDs, numeric save revisions, implementation labels, or the GPU simulation button. Confirm saving/saved/error/conflict and real recovery controls remain usable, and meaningful learning Version and Submission history are still accessible. Internal test IDs and revision fields are not required to be removed.

12. **AC-10 — Accessibility and narrow screens.** Use keyboard-only navigation through toolbar, Skill list, summary, board, Task movement, connection alternatives, and Review where authorized. Check focus after closing temporary views. At a narrow viewport, assert full-screen details, usable column selection/horizontal navigation, and readable errors. Repeat relevant list-to-learning workflows without WebGPU and under injected renderer failure; preserve the CPU document and exercise the actual recovery action.

13. **Harness and reporting.** Map every acceptance criterion to observable assertions in implementation tickets. New browser checks must consume the current build, declare build/database requirements, and use isolated ports/databases before parallel execution. Run focused affected checks during fixes and current full checks after the last change before review handoff. Existing regression checks alone do not establish this feature's acceptance. No acceptance tests or performance gates have been executed as part of publishing this spec; browser functionality is not proof of the separate headed P1 performance contract.

## Out of Scope

- Implementing only personal Kanban while silently dropping Coach/Learner scope.
- A cross-Skill/global Task Board or moving Tasks between Skills through column drag.
- Bulk many-selected-Skills-to-one connection gestures, arbitrary relationship types, cyclic graphs, or changed prerequisite semantics.
- New Mastery, XP, Access, Override, Approval, Version-migration, or publication rules.
- Learner editing of official Task definitions or adding private Tasks to an Enrollment in this release.
- Automatic Submission, Approval, or learner card movement caused by Review outcomes.
- Deadlines, priorities, labels, checklists, collaboration, and a new localization system.
- Restoration of archived Tasks, destructive deletion of history, or canvas undo of learning/Review history.
- Replacement of the Rust/WebGPU engine, WebGL rendering, automatic graph layout, or a mobile touch-gesture canvas rewrite.
- A new performance target, removal of existing performance gates, or claims that the current redesign has passed them.
- Implementation, implementation-ticket decomposition, commits, or deployment as part of this specification-publication task.
