# Measure P1 responsiveness with frame time and an in-app latency proxy

The P1 gate keeps its workload and its two numbers: on 1,000 cards, about 200 visible cards, and 2,000 connections with HTML labels, p95 frame interval at most 20 ms and p95 input latency at most 50 ms during pan, zoom, and drag. What changes is how those numbers are measured. Frame interval is taken from consecutive animation-frame timestamps during active motion. Input latency is an in-app proxy: from the browser's input `timeStamp` to the first animation frame after both the canvas and the HTML labels have committed the state produced by that input, plus one nominal display refresh interval as an estimate of presentation. The proxy is named `input_to_frame_proxy_ms` and every report states that it does not observe compositor output, scanout, or physical pixels.

This replaces the `gurow-p1-v1` requirement of a demonstrated input → canvas revision → label revision → hardware presentation timestamp chain, or a calibrated ≥240 fps optical rig. On the reference host that chain was structurally unavailable (#34 `UNSUPPORTED`, 0/18 attributable chains) and the optical rig did not exist (#41), so the gate could only ever be `NOT_MEASURED`. Browser standards offer no substitute for continuous input: Event Timing excludes `wheel` and `pointermove`. Comparable canvas editors gate on frame time rather than photon latency; Figma tracks average and maximum frame time on GPU-enabled headless VMs and a few real laptops, and tldraw reports per-interaction p95 frame time. A measurable proxy with stated limits is more useful to this prototype than an exact metric that cannot be acquired.

Sampling is simplified to match: three 30-second runs per scenario are pooled into one per-scenario p95, pacing and visibility are sanity checks rather than per-sample accounting, and unresolved inputs at the end of a run are charged the time until the run ends instead of voiding the metric. A controlled delay injected into the application update and, separately, into label commit must visibly shift the proxy, which guards against the proxy silently measuring the wrong frame.

The trade-off is a weaker claim. A P1 PASS means the editor's main thread, renderer submission, and label commit keep up with the workload in a real headed hardware browser; it does not prove end-to-end photon latency, and the true visible latency can exceed the proxy by compositor and scanout time. If a later product decision needs that claim, it requires a new measurement decision rather than a reinterpretation of P1 results. Results from different contract IDs are never combined.

Amended 2026-09-30 (contract `gurow-p1-v3`): the proxy's endpoint is `performance.now()` when the resolving rAF callback starts, not the rAF timestamp. Chromium stamps a frame when it is issued, so a callback delayed by a busy main thread carries an earlier timestamp; the first v2 sanity capture showed an 80 ms injected label-commit delay moving the timestamp-based proxy by only 9.6 ms. Frame intervals still use rAF timestamps. No acceptance series ran under v2.

Amended 2026-09-30 (contract `gurow-p1-v4`): a run is invalid only when the driver fails to send its load. On the reference host a 42–79 ms frame time made Chromium hold wheel input back (about 900 and 600 of 3,600 inputs reached the page, with seconds of queueing), which v3 classified as `NOT_MEASURED` and so hid an overloaded application. A run whose page received fewer than 80% of the schedule now stays valid and can fail, but never pass.
