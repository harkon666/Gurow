# Sign in with Better Auth email/password sessions

Accounts sign in with email and password through Better Auth, a self-hosted TypeScript library mounted in the Hono backend under `/api/auth` and stored in PostgreSQL through its Drizzle adapter. Better Auth's user model is the domain `accounts` table, so a session cookie identifies an Account directly and the backend derives acting authority only from that session (SPEC decision 20). Sessions, credentials and verification tokens use separate `auth_*` tables; the credential table is not called "account" to avoid confusion with the domain Account. The controlled P2 fixture identity remains a test-only resolver and is never wired into the served backend.

Verified-email state is the `email_verified` column. Only redeeming a verification link sent to the address sets it; it is not a sign-up or profile input, so a client cannot claim a verified address, and the Enrollment Invitation check reads the same column. Sign-in does not require verification, because personal learning needs none; only invitation acceptance does. The earlier `email_verified_at` timestamp was replaced by this boolean, keeping the identity integration as the single source of the state.

The browser reaches the backend through a same-origin `/api` forwarder in the frontend server, so the session stays an httpOnly first-party cookie and no token is handled by application code. Production therefore requires the frontend and `/api` to share one public origin (`BETTER_AUTH_URL`), a secret of at least 32 random characters (`BETTER_AUTH_SECRET`), HTTPS so the cookie is marked secure, and an email delivery provider behind the verification mailer. No delivery provider is integrated: the served backend logs verification links, which is sufficient for local development and tests but not for production.

Better Auth was chosen over a hosted provider (Clerk, Auth0) because sign-in, verification and session checks run locally against the real database without third-party accounts, so integration tests exercise the actual mechanism rather than a test mode. It was chosen over generic OIDC (for example Google) because local tests would otherwise rely on a stand-in issuer, and over magic links because those make every sign-in depend on email delivery. The cost is that Gurow stores password hashes and owns password-related lifecycle: password reset, email change, Account deletion and social sign-in are deferred Account lifecycle policies. Better Auth can add OAuth providers later without changing the Account table.
