# Reapply kept editor work as a new, validated save

[ADR 0016](0016-save-editor-snapshots-with-revision-checks.md) rejects stale saves and keeps the unsaved local changes for recovery. This decision sets how that kept work is stored, offered and brought back, for a personal Path, a Coach's Draft and a published Version's Canvas Layout.

While an editor holds work the backend has not accepted (a pending, failed, refused or stale save), the browser keeps it in local storage as one record: the accepted document the work was based on, the owner's local document, and the base revision. The record is keyed and checked by Account, editing context (personal Path, Draft or layout), Path and Learning Path Version, so another Account, another Path, or the next Draft of the same Path never reads it. Its record format, the canvas `format_version`, the concurrency revision and the Version identity are separate fields and are never substituted for one another. A record that is not whole and coherent (one card per Skill, connections between two of its cards, each Task under one Skill) is removed and reported, never restored in part. Records whose changes the accepted document already holds, for example because the closing save of an interrupted tab succeeded, are dropped silently.

Kept work is offered, never sent on its own. After a stale save the conflict lists the local changes and lets the owner reapply them, show the accepted version while keeping them aside, or discard them; on reopening, work kept by an interrupted session is offered the same way. Reapplying reads the accepted document and applies the owner's changes onto it by a three-way merge against the record's base: fields, Skills, Tasks, card moves and connections the owner changed take the owner's value, and everything else, including what was saved elsewhere meanwhile, stays as accepted. The result is sent as an ordinary save against the accepted revision, so the backend validates it (a merged connection can form a Prerequisite cycle) and refuses it if the revision moved again. Any refusal keeps the work. One reapplication runs at a time, and the editor is locked while it runs; an edit that still reaches the editor meanwhile (a window keyboard shortcut) is kept as work of its own when the reapplied document replaces what the editor shows, never dropped.

The merge was chosen over replacing the accepted document with the local one because a replacement would silently undo another tab's accepted changes, which ADR 0016 rules out, and over a field-by-field conflict dialog because the MVP editor cannot remove Skills or Tasks, which leaves few genuine conflicts. The cost is that where both sides changed the same field the owner's reapplied value wins without a further question; the conflict's change list is the owner's chance to inspect what will be applied. Kept work lives in one browser only and is lost with its storage.
