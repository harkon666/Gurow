# Persist the backend with Drizzle over Bun's PostgreSQL client

The Bun/Hono backend stores learning-domain data in PostgreSQL through Drizzle ORM, using Bun's built-in `Bun.sql` client as the driver (`drizzle-orm/bun-sql`). The schema is declared in TypeScript; `drizzle-kit` generates numbered SQL migrations that are committed, reviewed and edited like hand-written SQL. Rules that must hold under concurrency, such as one Enrollment per Account and Learning Path Version, are database constraints in those migrations, and request handlers rely on them with `ON CONFLICT`, row locks and transactions rather than on read-then-write checks.

Drizzle was chosen over writing raw `Bun.sql` queries because roughly two dozen MVP tickets will add many related tables (Workspaces, Versions, Enrollments, Submissions, Reviews, XP, Mastery), and most code is written by agents: a schema-derived type catches a wrong column or type at compile time instead of in an integration test. Its query overhead (reported within about 10–30% of raw SQL) is small against database round trips for this workload, and `sql` templates remain available for statements it does not model. Prisma was not chosen because its separate schema language and query engine sit further from the SQL constraints and transactions the domain rules depend on.

`Bun.sql` was chosen over postgres.js because it needs no extra dependency. Early Bun versions had problems with concurrent statements; on Bun 1.4.2, 250 concurrent transactions combining `SELECT … FOR UPDATE`, updates and `INSERT … ON CONFLICT` completed without error and with exact results (2026-10-04). If that changes, switching the driver to postgres.js is a one-line change in the database client module.

Local development and tests use one PostgreSQL 18 container from `compose.yaml`, bound to `127.0.0.1:5433`. Integration tests create and migrate a separate `gurow_test` database and empty it between tests; they never use the development database or other local containers.
