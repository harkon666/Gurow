# Save Task Boards whole against their own revision

[ADR 0027](0027-separate-task-board-organization-from-assessment.md) keeps board organization apart from assessment and ties a personal board's Completion Column to Task completion. This decision sets how a personal board is stored and saved, and how it stays coherent with the Path document.

A Skill's board is stored apart from the Path document: its columns (identity, name, order, and the Completion Column role) and one card per active Task. It has its own concurrency revision, so arranging a board never makes an open editor stale, and a document save never makes a board stale unless it changed the board's Tasks. The board is created on its first opening, which places the existing active Tasks once (completed ones in the Completion Column, the others in the first column, in their saved order) without replaying any completion.

A board change is saved whole against the revision its author saw ([ADR 0016](0016-save-editor-snapshots-with-revision-checks.md)): the server checks the complete result at once. Every active Task of the Skill must be on exactly one card and no other Task may be, so removing a column always names where its Tasks go. Cards crossing the Completion Column's boundary complete or uncomplete their Tasks in the same transaction, under the existing Access and XP Award/Correction rules; Access is checked once on the state before the save, and a refused completion refuses the whole save. A save that repeats the accepted arrangement succeeds without changes even on an old revision, so a retry after a lost answer records nothing twice. Any other stale save changes nothing and answers the current board.

The other entry points keep an opened board coherent in their own transactions and advance its revision: a document save adds a card for a new Task (end of the first column that is not the Completion Column) and removes the card of a deleted Task, archival removes the Task's card, and the retained completion action moves the card across the boundary. A deferred database trigger checks at commit that a card is in the Completion Column exactly when its Task is completed, that no archived Task has a card, and that each board has one Completion Column and another column.

In the browser, board edits are kept as intents (move this Task there, remove that column into this one) on top of the last accepted board, and that base never changes without the owner's decision. A save waits while this tab's Tasks for the Skill differ from the board's, so a new or deleted Task reaches the backend first; only intents never sent follow a newer board on their own, and only when it differs by added or removed cards. A refused or failed save keeps the intents, and Retry sends them on the same revision. A stale save, or a newer board read while intents wait for Retry, is a conflict: the owner reapplies them to the newer board or discards them. An intent that no longer applies (its column was removed, or its Task deleted or archived, elsewhere) is kept and shown until the owner redirects it or discards it; only a Task this tab created and has not saved yet (or saved after the board was read) makes an intent wait; a Task this tab's document still holds but a board read after that document no longer has was removed elsewhere, is reported, and neither shows nor holds the board back. A save's answer acknowledges exactly the intents it carried. After a save whose answer was lost, the next save is sent even if the local board equals the accepted one, so only the backend's answer can call it saved. Deleting or archiving a Task from the board drops that Task's own intents. A board read that an accepted save or a newer read has overtaken is ignored, so the board never goes back to an older revision. After an accepted save the learning records are read again rather than taken from its answer, so a reward change answered meanwhile is never hidden. They are read again too when a Skill's board is first read, and whenever a board read, reapplied onto or discarded to holds other Tasks in its Completion Column than the board it replaces. A conflicting board keeps the document it was read after, so reapplying or discarding onto it still tells Tasks removed elsewhere from Tasks on their way. Consequences shown before a column is removed are computed on the board a save would send, including Tasks added elsewhere that this tab's document does not show yet.

New column IDs are client-generated; inserting one never updates a column of another board, even when a concurrent save of another Path claims the same ID, and such a save is refused whole.

Saving the whole board was chosen over per-operation requests because the server can validate the final membership and completion of an edit as one result, which a column removal that also replaces the Completion Column needs. The cost is sending every column on each edit, which is small for one Skill's board, and that two tabs editing the same board conflict even on unrelated columns; the conflict keeps both sides recoverable. Intents survive closing and reopening the board in the same tab, but not a page reload, which asks before leaving while board changes are unsaved.
